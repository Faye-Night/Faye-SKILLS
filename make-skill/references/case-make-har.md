# 案例复盘：make-har 是怎么切的

同一个仓库里的 `make-har` 是本 skill 的第一个成品。它在切分上做了四个决定，值得复用。

## 一、正文只留"决策与顺序"，细节下沉

`make-har` 的原始素材有：CDP 探测方法、SPA bundle 逆向过程、leveldb 读取凭据、qd 引擎源码行号、断言求值顺序、jinja 过滤器清单、`api://` 协议解析……全部塞正文会超过 400 行，且 90% 的内容单次任务里用不到。

切法：

| 内容 | 去处 | 判据 |
| --- | --- | --- |
| 五个阶段该按什么顺序做 | 正文 | 每次都要走 |
| 断言优先级、`__log__` 通道、jinja 三陷阱 | 正文 | 踩过就会再踩，必须动手前看到 |
| CDP 探测命令、leveldb 键编码 | `references/recon.md` | 只在"必须逆向"时才查 |
| 引擎源码行号、过滤器全清单、`api://` 解析 | `references/qd-engine.md` | 查表用，不需要记住 |

结果：正文 149 行，两个参考文件各 6~7 KB。加载 skill 只读正文，需要时才点开参考。

## 二、每个坑写成"会怎么坏 + 怎么改"

反例（没用）：

> 注意 `success_asserts` 的优先级问题。

正例（`make-har` 实际写法）：

> `failed_asserts` **优先级更高**，任一命中立刻判失败。所以别把 `"code":401` 之类只写进 success 的排除项，要显式写进 failed。

差别在于：前者只提示"有个坑"，后者直接给出错误的写法和正确的写法。写 skill 时回头看自己踩坑的那次——**当时的错误认知是什么**，把那个认知写出来并否定它。

## 三、规范不复制，只指向

`make-har` 最初在阶段五复述了三条目录命名规则（一个网站一个目录、网站名大写网址小写、`readme_{网站名}.md`）。问题：这三条同时写在仓库根的 `AGENTS.md` 里，两处维护必然漂移。

改法：删掉复述，写成「目录位置与命名规则以仓库根的 `AGENTS.md` 为准，**此处不重复**——那份文件是强制规范，本 skill 只管"怎么做"。落盘前先读它。」

**但注意适用边界**：`make-har` 放在 skill 仓库里对外发布时，那份 `AGENTS.md` 不在旁边了，指向就断了。所以发布版改成内联"没有规范时的默认约定"。判据是——**引用目标会不会跟着 skill 一起被复制**。会，就指向；不会，就内联。

## 四、可移植性必须在发布前测，不能靠看

`make-har` 从项目内 skill（`<项目根>/.dsh/skills/make-har/`）搬到独立仓库时，带过去 3 处断链：

- `[AGENTS.md](../../../AGENTS.md)` —— 相对路径在仓库里指向不存在的位置
- 「脱敏要求见 `AGENTS.md` 规则三」—— 引用目标不存在
- 「目录命名符合 `AGENTS.md`」—— 同上

**只看正文看不出来**，因为这些写法在源仓库里完全正常。有效的测法是：把整个 skill 目录复制到一个空目录，再逐条检查相对链接是否可达。`scripts/check_skill.py` 把这一步自动化了。

同理，硬编码绝对路径（盘符路径、`/home/<用户>/`）在源机器上也能跑通，换机器就废。

## 五、description 是唯一的入口

`make-har` 的 description 244 字符，含三组触发词：

- 中文动作词：抓取、逆向签到请求、编写 qd 模板、验证模板
- 具体标识符：`success_asserts`、`extract_variables`、`__log__`
- 英文兜底：`qd HAR authoring`、`sign-in API reverse engineering`、`HAR template validation`

理由是模型会话目录**只渲染 name 和 description**。用户说「帮我给某网站做每日签到」时，正文里的内容一个字都看不到，全靠 description 匹配上。所以 description 里要放**用户会说的词**，不是**你想描述的概念**。
